## Part 1 — How the graph works

### My graph and state

**Original graph:**
```text
START → read_request
          ├── wifi_help → END
          ├── password_help → END
          └── other_help → END
```

The shared state contains `message` (original input), `category` (identified topic), and `reply` (answer). `read_request` reads `message` and updates `category`; each help node reads the current state and updates `reply` using `data/helpdesk.json`, or asks a clarification question. Nodes return partial state updates, whereas a conditional edge only selects a next node. Each node receives the **merged current state**, not only the previous update. `START` and `END` mark entry/exit; `compile()` makes the graph executable.

## Part 2 — Model and tools

**Model/tool graph:**
```text
START → Model
          ├── Tool requested → ToolNode → ToolMessage → Model (loop)
          ├── No tool requested → END
          └── Tool limit reached → END
```

1. The conditional edge examines `AIMessage.tool_calls`; if present, it routes to `ToolNode`, otherwise `END`.
2. The **OpenAI model** requests tools; LangGraph's **ToolNode** executes the Python functions.
3. Tool results become `ToolMessage` entries in `MessagesState`, informing the next model decision.
4. Unlike Part 1's fixed keyword rules, tool selection depends on the model's reasoning and the previous tool results.

**Provider:** OpenAI. **Configured model:** `gpt-4.1-mini` (verify the exact `MODEL_NAME` in the recorded run metadata). **Limit:** `MAX_TOOL_ROUNDS = 5`, enforced in `part2.py` inside `call_model`, which returns a limit message when the count has been reached.

## Part 3 — Memory

**Conversation memory:** LangGraph `SqliteSaver` checkpoints messages, the current problem and attempted steps. A `thread_id` identifies one conversation; the implementation namespaces it with `user_id` as `user_id::thread_id`. A different thread cannot inherit the old problem. **User memory:** `preferences.sqlite`, keyed by `user_id`, keeps a saved reply-language preference across threads and process restarts.

`capture` reads the latest message, prior conversation state and the current user's preference; it updates `problem`, `steps_tried`, `preference` and `memory_source`. Reading `helpdesk.json` via `find_instructions` is **retrieval from a shared reference**, whereas recalling Kazakh for `demo-user-a` is **persisted user memory**. The scenario runner uses separate Python processes with preserved SQLite files to demonstrate restarts.

`tests/test_helpdesk.py` checks routing/case priority, the clarification node, instruction retrieval, operational/outage/unknown statuses, password-recovery status, draft JSON content, missing ticket details, SQLite persistence **across subprocess restarts**, and separation of users and threads. **Local result:** 14/14 pytest cases passed on Python 3.12.16 (verified after pinning dependencies). **CI:** `.github/workflows/tests.yml` runs pytest on GitHub Actions for pushes to `main`, pull requests and manual triggers, without a private API key. Actual model demonstrations are kept separate from keyless CI tests.

## Choices and limitations

LangGraph provides explicit graph routing and traceable tool execution; SQLite offers simple local persistence that survives restarts without hosting a database. `ChatOpenAI` was chosen for a tool-capable model; `pytest` and a fake memory planner make CI deterministic. Limitations: the demo works only with fictional service snapshots; it cannot send real tickets. Tool results and LLM wording may vary; the English step extractor only recognizes selected phrases, and the model may request an invalid step (as seen on the first S06 attempt). The five direct dependencies are pinned, but transitive packages are not locked. Conversation storage is intended for a local single-user demo, not production multi-worker use.
